### 关键设计：三类处置而非二分

预检把产物分三类，依据是"我们能确定什么"：
1. 内核模块（有 `.modinfo`）→ vermagic 精确比对
2. ELF → `e_machine` 架构比对
3. **认不出 → 放行**

第 3 类是既有测试逼出来的：原实现把"打不开/不是 ELF"判失败，结果 3 个既有
CLI 测试全红（它们的测试资产是文本不是 ELF）。但真问题是设计缺陷而非测试：
现实里有 shell/python 脚本、jar 等非 ELF 产物，判失败是**假阴性**——直接把
本来能用的组件推掉。假阴性比漏检更糟：漏检最多装完再报错，假阴性让合法装载
永远失败。已补 3 条测试守住（非 ELF 放行、空文件放行、真 ELF 仍拒）。

# P9 ferc bench 接真实装载（2026-11-25）

此前 `ferc bench` 的 Runner 是度量骨架，`elapsed_ms` 恒为 0、成败由"形态是否被
节点支持"决定。本轮接上真实装载。

## 改动

- `internal/cli/bench.go` 新增 `realBenchRunner(env, info, comp, faults)`：
  每个组合用**独立临时数据根目录**（`os.MkdirTemp` + `defer RemoveAll`）跑完整
  `install.New + resolve.Resolve + Apply`。复用同一个 root 会让后一个组合看到
  前一个的残留状态，"成功率"就不再是这个组合自己的成绩。
- `--real` 开关：不加时仍走度量骨架（零副作用）；加了才真下载、真注册、真起进程。
- 检查顺序按"前提的强弱"重排：**网络 > 形态兼容 > 组件与实验形态是否对得上**。
  网络在最前是因为它是物理前提——介质不在场时讨论"这个组件适配吗"没有意义。
- `stageOf` 新增 `isNetworkErr`：网络类失败（connectex / connection refused /
  i/o timeout / TLS handshake / no route to host / 介质不在场…）优先归到
  `download`。现场最常见的一类失败就是取不到包，不优先识别会让阶段分布失真。

## 实跑验证（真实二进制）

无代理时 `--real`：`elapsed_ms=21058`、阶段 `download`（真实网络超时）。
带代理时：走到 resolve（274ms 取到清单）后因 `DontCrack4Windows` release 403
失败——这是**真实情况**：Windows 无原生保活能力，`resolve` 必然带上 dontcrack
依赖，而那个仓的 release 取不到。

同一台机器上单独跑 `ferc install simple-web-shell --no-start` 成功（2 个组件、
凭据落 0600），证明 Runner 走的确实是同一条真实装载路径。

## 诚实边界

- `--real` 的成功率**依赖目标仓的 release 可达性**。DontCrack4Windows 当前
  403，因此 Windows 上的矩阵必然失败；这不是代码缺陷，是现场事实。
- 需要网络的测试用 `testing.Short()` 跳过，CI 无外网时不会红。
- 论文引用矩阵数据前，须在**目标平台**上实跑一遍，不能拿开发机结果代替。
