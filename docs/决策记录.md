# 决策记录

> 只记录课题提示词**未指定**、由实现方做的选择。

## D1 ParseModule 的 vermagic 精确相等

- **选择**：`Vermagic` 字段存 `.modinfo` 里 `vermagic=` 的原始值，比对时做
  **精确字符串相等**，不做任何版本模糊比较（不拆版本号、不比前缀）。
- **理由**：内核模块的 vermagic 包含内核版本、SMP/PREEMPT 等编译开关、
  甚至 GCC 版本。任何一项不同都会导致 `insmod` 报 `invalid module format`。
  模糊比较会把"看起来像"当成"能装"，而这正是课题要消灭的假阳性。
- **备选**：拆成结构化字段逐项比——更精细，但 vermagic 的格式由内核配置
  决定，没有稳定契约，拆解规则本身会随内核版本漂移。
- **影响面**：仅新增解析器；预检（F2）消费该字段。

## D2 真 .ko 测试件的获取方式

- **选择**：测试件由程序合成 ELF；真实 `.ko` 走环境变量 `EDGECAP_KO_DIR`，
  未设置时 `t.Skip` 并打印原因。
- **理由**：课题明确要求"测试件程序合成ELF；真.ko走EDGECAP_KO_DIR，未设则
  t.Skip并打印原因"，且禁止提交真实驱动/大二进制。
- **备选**：把一小段 .ko base64 嵌进测试——仍然算提交二进制产物，且不同
  内核版本编出的 .ko 无法通用。
- **影响面**：仅测试。

## D3 F3 非常驻断言的运行平台

- **选择**：`TestRuncoreIsNotResident` 用 `//go:build linux` 限定。
- **理由**：课题要求"枚举 /proc/*/comm"，这是 Linux 特有的判定方式；
  在 Windows/macOS 上只能跳过，而跳过又不能冒充通过，因此用构建标签
  让它根本不在那些平台上编译。
- **备选**：运行时 `runtime.GOOS != "linux"` 时 `t.Skip`——也能达到效果，
  但会让"未运行"和"已运行并通过"在输出里难以区分。
- **影响面**：仅测试。

## D4 对照开题反馈的符合性核对结论（2026-11-24）

本仓（执行侧）已支撑的部分：

| 开题反馈要求 | 对应实现 |
|---|---|
| 运行核装载后非常驻 | `internal/install/residency_test.go`，枚举 `/proc/*/comm` 断言无 ferc |
| 部署前二进制校验（vermagic 精确匹配） | `internal/artifact`，三类错误可区分不合并 |
| 校验失败不落盘 | `installBinaryChecked` 先预检后 moveFile，失败连 bin/ 都不建 |
| ELF 架构校验 | `ParseELF`，Static 只看 PT_INTERP 有无 |
| 归档包递归检查 | `InspectArchive`，架构冲突列文件 |
| 装载实验矩阵 | `internal/bench`，4 形态 × 3 网络 = 12 组合，CSV 列固定 |
| 四形态装载 | catalog 13 组件，`supervise` 六种托管机制 |

尚未支撑、论文须标注为设计目标的部分：

1. **OneKey 一次性密钥换证书**：本仓无 `x509`/`tls` 实现。《开题命题》对照点 6
   定位为 RQ1"信任建立"能力项，现为空缺。
2. **两级编排**：外部框架（KubeEdge/EdgeX）作为组件被装载、其内部编排自理的
   路径不存在。此为 RQ2 核心论据。
3. **`ferc bench` 的 `elapsed_ms` 全为 0**：Runner 是度量骨架，未接真实装载，
   耗时数据须等接入后才有。
4. **形态口径**：开题称四种形态（容器/静态二进制/内核模块/归档），
   catalog 实际只有 service/tool/supervisor 三类——因 catalog 描述的是
   FasterEdge 自有组件，未含内核模块与归档包样本。
